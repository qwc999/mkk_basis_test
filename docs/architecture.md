# Архитектура сервиса

## API и сохранение платежей (фича 1)

API создаёт платёж со статусом `pending`, `processed_at = null`, и возвращает его
сохранённое состояние. Outbox публикуется фоновым отправителем, а отдельный процесс
consumer выполняет эмуляцию и сохраняет результат (фича 2, описана ниже).
HTTP-запросов к webhook, ограниченных retry и DLQ пока нет.

`app/config.py` читает настройки, `app/db.py` создаёт асинхронный engine и сессии,
`app/models.py` описывает схему, `app/schemas.py` — валидацию и ответы,
`app/api.py` — аутентификацию и маршруты, `app/payments.py` — транзакцию создания.
Для каждого HTTP-запроса используется отдельная `AsyncSession`.
Общих базовых репозиториев и дополнительных DI-фреймворков нет.

## Данные

Идентификаторы — серверные UUID. Сумма проходит валидацию как `Decimal`, хранится
в `NUMERIC(18,2)` и возвращается строкой с двумя десятичными знаками.
Валидация проверяет положительность, диапазон и отсутствие ненулевых цифр после
второго знака, не округляя входное значение. `app/json_request.py` разбирает денежные
JSON-числа непосредственно в Decimal до валидации: стандартный разбор во float мог бы
потерять точность ещё до проверки количества десятичных знаков. Для клиентов
рекомендуется JSON-строка; metadata сохраняет обычные JSON-типы.

Валюта и статус хранятся строками с именованными CHECK-ограничениями.
Дополнительно БД проверяет положительную сумму, непустые описание и ключ,
тип JSON-объекта для metadata, длины строк и уникальность `idempotency_key`.
В ORM колонка `metadata` называется `payment_metadata`, поскольку `metadata`
зарезервировано SQLAlchemy. В HTTP-контракте имя остаётся `metadata`.
JSON хранится как PostgreSQL JSONB.

Все даты приложения создаются в UTC, колонки используют `TIMESTAMP WITH TIME ZONE`,
соединения PostgreSQL устанавливают часовой пояс UTC. Схема создаётся только Alembic;
миграции запускаются отдельной явной командой, не при старте каждого процесса API.

## Транзакция и конкурентная идемпотентность

`create_payment` открывает `session.begin()`. В этой транзакции выполняются:

1. `INSERT payments ... ON CONFLICT ON CONSTRAINT uq_payments_idempotency_key DO NOTHING RETURNING ...`.
2. Если платёж вставлен, добавляется ровно одна строка Outbox:
   `event_type = payments.new`, `payload = {"payment_id": "<UUID>"}`.
3. Транзакция фиксирует обе записи. Ошибка вставки, flush или commit откатывает обе.

Уникальность обеспечивает PostgreSQL, а не предварительная проверка существования
в Python. При гонке запросов с одним ключом PostgreSQL блокирует конкурирующую вставку
до завершения первой транзакции. Используется стандартный уровень `READ COMMITTED`:
последующий отдельный `SELECT` видит зафиксированный результат победившей транзакции.
Если первая транзакция откатилась, вторая может сама вставить платёж и событие.

Если вставка пропущена, приложение читает платёж по ключу и сравнивает валидированные
данные: Decimal, валюту, исходную строку описания, JSONB metadata и нормализованный URL.
Сравнение JSONB выполняется в PostgreSQL: порядок ключей вложенных объектов не влияет,
но JSON boolean и число различаются (`true` не равно `1`).
Пропущенный metadata нормализуется в `{}`. Изменение статуса не меняет исходные данные
запроса: повтор возвращает текущий сохранённый статус и исходную дату создания.
Совпадение даёт `202`, различие — `409`; обе ветки не добавляют Outbox.

Ключ глобален для единственного статического API-ключа, срок его действия не ограничен.
В этой фиче платежи не удаляются, изоляция транзакций не меняется на REPEATABLE READ.
Повторная публикация допустима; идемпотентность обработки описана ниже.

## Аутентификация, конфигурация и проверка

Зависимость маршрутов проверяет `X-API-Key` через `secrets.compare_digest`.
Для отсутствующего и неверного ключа используется одинаковый ответ `401`.
Служебные HTTP-страницы документации отключены.
Ошибки конфигурации показывают имена настроек, не значения. Значения ключа и DSN
представлены `SecretStr`, SQLAlchemy скрывает параметры SQL в исключениях.
Логи приложения содержат события запуска, остановки и UUID принятого платежа;
тело платежа, ключи и URL подключения не логируются.

Интеграционные тесты применяют Alembic к выделенной PostgreSQL с БД и пользователем
`payments_test`; до любых изменений проверяются оба имени и драйвер URL.
Compose для тестов выделяет отдельный контейнер, сеть и tmpfs без рабочего volume.
В тестах проверяются API, ограничения БД, реальный откат при ошибке вставки Outbox,
повторы, конфликтующие данные и одновременные запросы с одним ключом.

## Асинхронная обработка (фича 2)

Процесс `python -m app.worker` объединяет одного подписчика FastStream и фоновую задачу
отправителя Outbox. Compose содержит четыре сервиса: postgres, rabbitmq, api, consumer.
API зависит только от PostgreSQL; при недоступном RabbitMQ он продолжает создавать платежи.
`DatabaseSettings` разделяет настройки БД между API, worker и Alembic. `Settings` добавляет
API_KEY, `WorkerSettings` — RabbitMQ и интервалы. Worker не использует API_KEY.
Версии зависимостей первой фичи сохранены, добавлен FastStream 0.7.7 с RabbitMQ backend.

### Топология и публикация

Durable direct exchange `payments` связан с durable очередью `payments.new` по routing key
`payments.new`. Топология объявляется при запуске подписчика до старта отправителя.
Сообщения persistent, body — `{"payment_id":"<UUID>"}`, message_id — UUID строки Outbox.
RabbitMQ хранит сообщения и топологию на отдельном volume со стабильным hostname узла.

Канал использует `publisher_confirms=True`, `on_return_raises=True`, а публикация —
`mandatory=True`. Возвращённое из-за отсутствия маршрута сообщение вызывает исключение.
Отправитель дополнительно требует положительное подтверждение `Basic.Ack`; одного завершения
вызова publish недостаточно. Внешний `asyncio.timeout` ограничивает и ожидание восстановления
соединения, и отправку/подтверждение; AMQP timeout также передаётся FastStream.

Одна итерация отправителя открывает отдельную транзакцию, выбирает одно событие
`payments.new` с `published_at IS NULL`, упорядоченное по `(created_at, id)`, через
`FOR UPDATE SKIP LOCKED`, публикует и только после подтверждения записывает published_at в UTC.
Commit фиксирует отметку. Исключение, timeout или отмена откатывают транзакцию и освобождают
блокировку. Другой отправитель пропускает занятую запись и может обработать следующую.
Большая пачка строк во время сетевого вызова не блокируется.

Миграция 0002 добавляет частичный индекс `(created_at, id)` только для неопубликованных
`payments.new`, соответствующий фильтру и порядку polling-запроса. Начальная миграция не менялась.
После успешной отправки следующая запись выбирается сразу; при пустом Outbox выдерживается
OUTBOX_POLL_INTERVAL. Технический сбой публикации логируется без URL и откладывает следующую
попытку минимум на одну секунду. Опубликованные записи не удаляются.

Гарантия — **at least once**. Если брокер принял сообщение, но процесс не успел зафиксировать
published_at (включая ошибку commit), событие может уйти повторно. Распределённой транзакции
и обещания exactly once нет.

### Обработка и ACK

Подписчик получает ровно одно неподтверждённое сообщение одновременно: prefetch_count=1,
ручная политика AckPolicy.MANUAL. Декодирование оставляет raw body, чтобы malformed JSON
попал в явную валидацию PaymentEvent, а не остался необработанным до вызова handler.

В отдельной AsyncSession и транзакции обработчик блокирует Payment через `FOR UPDATE`.
Для pending вызывается подменяемый `simulate_payment`: `asyncio.sleep` со случайной задержкой
2–5 секунд, затем succeeded с вероятностью 90% или failed с вероятностью 10%.
Сохраняются окончательный статус и processed_at в UTC, транзакция фиксируется; только затем
вызывается ACK. Блокировка удерживается во время эмуляции — намеренное упрощение этого этапа.
На будущую отправку webhook эта транзакция не распространяется.

Для succeeded/failed эмуляция пропускается, статус и processed_at не меняются. После проверки
состояния сообщение подтверждается. Дедупликация основана на payment_id, а не message_id.
Два конкурентных обработчика одного платежа сериализуются блокировкой и используют один
зафиксированный результат. Статусов processing и lease нет.

Падение до commit возвращает платёж в pending; повторная эмуляция до первого сохранённого
результата допустима. Падение после commit до ACK приводит к повторной доставке, которая
видит окончательный статус и не пересчитывает результат. Failed — завершённая бизнес-операция,
она подтверждается и не является причиной технического retry.

### Ошибки, восстановление и остановка

Некорректный JSON/UUID/контракт сообщения и несуществующий Payment логируются без тела
сообщения и отклоняются без requeue. До добавления DLQ такие сообщения отбрасываются.
Техническое исключение обработчика или БД не приводит к ACK: выдерживается пауза 2 секунды,
затем NACK с requeue. При prefetch=1 неподтверждённое сообщение удерживает потребление
во время паузы. Это временная неограниченная стратегия до трёх попыток, backoff и DLQ
в следующей фиче; ни retry-очередей, ни счётчика попыток пока нет.

FastStream/aio-pika используют robust-соединение с восстановлением каналов, топологии и
подписки. Начальная недоступность брокера приводит к повторным попыткам соединения с паузой.
Sender продолжает работать после восстановления; ошибка публикации оставляет событие в БД.
Ошибка ACK/NACK, которую нельзя обработать на текущем канале, завершает worker с ошибкой,
после чего Compose перезапускает процесс и брокер возвращает неподтверждённые сообщения.

Главная корутина наблюдает за задачей отправителя: неожиданное исключение или нормальное
завершение этой бесконечной задачи останавливает worker, а не оставляет живой контейнер
без отправителя. SIGTERM/SIGINT инициируют остановку: отменяется sender с откатом его
незавершённой транзакции, подписчик получает до 10 секунд на завершение handler, затем
закрываются канал, AMQP-соединение и engine. Неподтверждённые сообщения возвращаются брокеру.
Compose даёт consumer 20 секунд на остановку и перезапускает его при аварийном выходе.

Тесты используют выделенный RabbitMQ с пользователем и vhost payments_test, отдельным volume
и без рабочих секретов. Реальные публикации проверяют confirms, отсутствие маршрута,
persistent/message_id, конкурентных отправителей и восстановление соединений. PostgreSQL
проверяет блокировки и rollback. Эмуляция в тестах детерминирована, реальные задержки и
штатный перезапуск RabbitMQ с сохранением очереди проверяются через
`python scripts/smoke_processing.py` в отдельном Compose-проекте со случайными тестовыми
секретами. Сценарий также проверяет отсутствие секретов и полных URL в логах API/worker.
